# `generated_support` — the physical carrier assembly

How closed projection outputs become ONE exported support shell, without any raw
or unproved token crossing the wall.

That is the whole question this home answers, and it is a physical one. The wall
declares one carrier and the carrier has a fixed set of seats; several
projections have material for those seats; somebody has to say which material
fills which seat, that it all belongs to one declaration, and that nothing was
delivered twice or delivered somewhere it was never planned. This home is that
somebody.

## What it is not

**Not a projection kind.** It plans nothing, renders no unit of its own, and has
no membership. Every token it places was rendered and PROVED somewhere else; it
reads terminals and never plans over them.

**Not a semantic owner.** It decides no meaning. Which rows a descriptor states,
which subject an evaluation copy stands over, which selection a copy reads — all
of it arrives as data from the home that owns it.

**Not a provider registry.** Naming which providers of descriptor material exist
is `composition`'s declaration, and it is a composition rather than an inventory.
This home is downstream of that question entirely: it is handed material and asks
whether it physically composes into one carrier. Assembly is PHYSICAL;
composition is the provider registry. Neither answers the other's question.

## What crosses, and what cannot

The input is CLOSED EXPANSIONS — terminal values, the only values in these
services from which proved cargo is reachable — plus the delivery dispositions
that say what happened where nothing was produced, plus the published schema
expectation the carrier's gate is pinned against.

No loose tree can enter. There is no seat anywhere in this home that takes a
token tree on its own: cargo is read off a terminal's own proved partition, and
the road that reads it records which terminal and which partition it came from.
That is what makes "no raw or unproved token crossing" a shape rather than a
review note.

The output is a typed assembly, and the shell renderer consumes that and nothing
else. The carrier's own composition road is crate-internal, so the public road to
an exported shell runs through an assembly that verified.

## The five things the assembly verifies

Each with a typed refusal naming exactly what disagreed:

1. **One root.** Every carried axis's source terminal stands under the same
   captured-declaration or owner-content root the assembly does. A carrier
   composing two declarations' cargo is one exported name delivering material
   from two places.
2. **One published schema expectation.** The expectation the carrier's gate is
   pinned against is the one these services publish, at full width. A second
   expectation minted beside it would put a pin in the shell that no publication
   act wrote.
3. **Every carried unit consumed exactly once.** Two axes reading one terminal's
   one partition would deliver those tokens twice into one target.
4. **No unit reaches two destinations.** An axis reads the carrier partition its
   own delivery names and no other. Cargo read from the declaration-site
   partition into a carrier seat is material compiled in the consumer's normal
   build AND in its test target — the exact tax the wall exists to refuse.
5. **The tokens are the source's own.** The cargo handed for an axis is
   token-for-token the cargo that terminal's named partition proved. That is the
   seat at which the shell's eventual bytes commit to the source expansion
   identities: the assembly records the identity beside tokens it proved belong
   to it, and the shell is rendered from the assembly in one act.

## The cargo is composed axes, never one product

Three axes, three DIFFERENT materials, and that is why they are not one enum with
a payload:

- **trial cargo** is a DECLARED payload — the harness's row vocabulary, every
  seat refused at the carrier's own door;
- **evaluation cargo** is PROVED cargo off a terminal — a local subject, the
  selections it reads, and one closed expansion's tokens;
- **bench cargo** is proved cargo on the same terms.

Each axis is `Absent`, carrying the disposition that says what happened to the
projection that would have filled it, or `Carried`. Trials-only,
evaluation-only, and both are lawful: a door that holds no caller-supplied rows
still has evaluation copies to deliver, and an empty trials seat beside carried
deferred cargo is exactly what such a door renders.

**The bench axis's carried arm is honestly typed and its vehicle is a stated
opening condition.** The carrier's published grammar has two cargo seats, and
neither is the bench seat: the bench material rides the same gate today, and the
seat that would carry it separately is reserved rather than written. So a carried
bench axis refuses, and the refusal names the condition — the bench seat filling
— rather than pretending the material had somewhere to go.

## The seats

`types.rs` declares: the axis roster, the axis cargo shape, one terminal's proved
cargo, the closed issue set, the assembly itself, and the joined value a door
hands back. Its own child `type_guard.rs` holds every road that reaches a private
seat — reading cargo off a terminal, assembling the verified whole, and the
refusal body — which is what makes "nothing unproved is in an assembly"
structural: there is no second seam that can build one. `establish.rs` is the
verification pass itself, pure, reading axes through the same answers any caller
gets. `type_contract.rs` states the declarative tables: the family's declared
shape, and which carrier partition each axis delivers from. `render.rs` is the
one road from a verified assembly to a rendered carrier.
